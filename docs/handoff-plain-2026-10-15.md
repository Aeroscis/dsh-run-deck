## 用户是谁、怎么跟他说话

- 中文母语，**极其讨厌行话堆砌**。上一轮我用 PTY / ConPTY / endsPattern / isBackground / 句柄 / run 记录 这类词写了一堆分析，他回的原话是：「有一说一，我完全没看懂，你也太不说人话了」。
- 所以：**每个术语第一次出现必须先用一句人话解释**，或者干脆换成日常说法。
  - PTY / ConPTY → 「后台开的一个隐藏的命令行窗口，程序在里面跑」
  - endsPattern → 「脚本输出里约定的那句话，用来判断"我起来了"」
  - isBackground → 「这条命令跑起来后不会自己结束（长驻）」
  - run 记录 / 句柄 → 「这条命令这一次执行的那笔账 / 那根牵着它的线」
- 回答顺序固定：**先 3 句话以内的结论 → 再打比方讲为什么 → 最后给 2~3 个选项 + 推荐，问他选哪个**。
- 禁止：「可能是…」「应该没问题」；禁止只给文件名+行号就当他看懂了（行号可以放后面当证据，不要当解释）。
- 要根因 + 证据（日志时间戳、代码实际行为、跑一遍验证），不要猜测。

### 绿点到底是什么（这是关键，必须讲清）

- 那个绿有两部分：**按钮外侧一圈绿边框** + **右边一个圆点**。
- 判定条件只有一个：**这条命令这一次执行的进程还活着**（代码：`src/manager.ts` 里 `listButtons()` 找这条 entry 有没有状态不是 `exited` 的执行记录，约 989~1003 行；界面在 `src/client.tsx` 约 1119、1136~1151 行渲染）。
- 熄掉只有两条路：
  1. 进程自己退出（代码：`settleRun()`，`src/manager.ts` 约 672 行）
  2. **用户再点一次那个绿按钮** = 给进程发 Ctrl+C（代码：`stopRun()`，`src/manager.ts` 约 853 行；Windows 上就是往那个隐藏命令行窗口写一个 `\x03`，脚本里挂在 SIGINT 上的清理代码会跑）
- **「关掉浏览器」这件事插件完全收不到，它没有任何代码路径会因为浏览器关闭而熄灯。** 界面上不做端口探测、不跟踪窗口。

### 为什么 build 的绿一直不灭

`start_gallery_web.py --build` 进的是这个脚本的 `run_build()`（`D:\Flora\ProgramProjects\jin\start_gallery_web.py` 约 315~336 行）：

1. 先真的构建；
2. 然后起 `vite preview` 服务器；
3. 打印 `built gallery served at http://localhost:5180/` —— **就是这行字让它变绿的，也是这行字让界面自动打开浏览器**；
4. 然后 `return stream(child)` —— **卡在这里等 Ctrl+C，进程不结束**。

所以：**构建早在 1 分钟内就干完了，但进程没干完（它还要一直服务）**。绿灯的含义其实是「那台预览服务器还活着」，不是「还在构建」，更不是「浏览器页面还开着」。关浏览器只关掉了"看的人"，服务器还在跑。

### 为什么 jin web / jin desktop 看起来会灭（其中一个是错觉）

- **desktop 是真的**：`start_gallery_desktop.py` 会一直等它启动的那个 `jin-gallery.exe`（约 216~247 行 `stream(child)`）。**窗口的命 = 进程的命**，关掉窗口 → 进程退出 → 灯灭。这是它脚本形状的副产品，不是通用规律。
- **web 是错觉**：日志里显示他那次点 `jin · web` 时，5180 端口已经被 build 起的 preview 占着，脚本走到「已经有一个画廊在跑」这一支：打印一行 `a gallery is already running at …` 然后**立刻 exit 0**（同一文件约 296~306 行）。也就是**它自己 1 秒后就退了**，跟关不关浏览器无关。

### 「没有输出窗口」这件事的事实

- 这条路用的是「不显示任何窗口」的隐藏命令行窗口（当初还专门写了个探针 `_probe/run/ptywindow.mjs` 确认桌面上不会冒窗口）。
- `.dsh/run.json` 里那个 `presentation: { panel, reveal }`（写着"专用面板、总是显示"）**是个死字段**：解析了（`src/config.ts` 约 215~223 行），但界面上没有任何地方读它。
- 输出其实**有**出口，但很窄：只把**最近 6 行**存进记录（`src/manager.ts` 约 109 行），只在那个齿轮 ⚙ 面板里显示（`src/client.tsx` 约 1732 行）。README 的前一版交接里自己写着「未做：完整输出面板（现在只有最近 6 行）」。
- 宿主的日志只记关键事件（起/停/就绪/告警），**不逐行记脚本输出**。

## 别破的硬约束（改代码时必须守）

1. **命令只能来自项目里的 `.dsh/run.json` 字面量**。接口只接受 `{项目路径, entry id}` 这样的"指针"，绝不接受自由命令，也不扫目录找可执行文件。
2. **进程必须由宿主的 `subprocess` 服务持有**（它开的是隐藏 PTY）。这是为了：Ctrl+C 能真的送进进程组（脚本的清尾代码才会跑），以及插件卸载/宿主退出时它会把整棵进程树收掉。已经踩过的坑：进程脱离监管后，脚本退了但 `vite preview` 还活着，端口一直被占。
3. 破坏性操作要有确认；不要把界面变成"无确认执行任意脚本"的通路。

## 关于「要不要让脚本弹出可见窗口」——我上一轮的分析（可复核，但方向请保留）

用户的直觉是：弹个窗口 → 关掉窗口就等于停掉它 → 灯就灭了。这个方向**不是不能做，但要付代价**：

1. 要可见窗口就得自己用 `CREATE_NEW_CONSOLE`/`start` 起进程，那条链**不在宿主 `subprocess` 服务的登记里**，等于破坏上面第 2 条约束 → 又会出现"脚本退了、子进程还占着端口"。
2. 窗口是别人的，插件**读不到它的输出**。而现在"我起来了"的判定、自动打开浏览器、就绪后接力下一条命令，**全都依赖读输出**（`src/exec.ts` 约 346~378 行）。要保住就得同时再 tee 一份输出，复杂度上一个台阶。
3. Windows 上关控制台窗口发的是另一种事件（CTRL_CLOSE_EVENT），只给约 5 秒宽限，脚本的 SIGINT 清理**不保证跑完** → 还是会留孤儿。
4. 每个命令一个窗口会撒满桌面；而 jin 的脚本**专门为了不冒出空 cmd 窗口才绕开 pnpm**（`start_gallery_web.py` 约 93~107 行有注释）。方向相反。
5. 他想要"关标签就停"其实已有对应物：宿主的侧栏终端（`@deepseek-ai/dsh-api-terminal-controller`）**接不了现成的进程**——它只能新建一个 shell、按会话持有，而且明确"关标签 ≠ 杀进程"。

### 我建议的两个方案（讲人话给他选）

- **方案 A（先做，最省事，纯界面）**：把每条命令的"最近 6 行"扩到两三百行，并在浮动条上点那条正在跑的命令就能展开看它的输出（现有 2.5 秒轮询就够，不需要新通路）。顺手处理 `presentation` 这个死字段：要么真接上，要么从类型里删掉，别让配置文件承诺界面没有的东西。
- **方案 B（紧接着做，才是真正解决"绿灯常亮"）**：给 run.json 加一个"**说好就绪之后就算这条跑完了**"的开关（比如 `exitOnReady: true`）。效果：就绪 → 灯灭（或换一种"还在后台服务"的样子），但**进程继续服务、还能点停、输出继续长**。
  注意：不能直接把状态写成 `exited`，因为 `stopRun()` 会拒绝已经 exited 的执行记录（`src/manager.ts` 约 858~860 行），得真加一个新状态。

另外可以顺带提一句给他选：**把"构建"和"起服务"拆成两条命令**（构建那条跑完就退、灯自己灭；服务那条是长驻）。这也是 VS Code 的习惯做法，`jin` 的脚本目前是"一条命令干两件事"，所以才卡绿。
